# Minesweeper skills and private generation

Delivery consists of the project router `antislope/SKILL.md`, the code workflow `antislope/minesweeper/SKILL.md`, a bundled Node helper, and the existing TypeScript runtime/browser UI. The generator reference is for the worker only; the facilitating conversation must not load it or private exercises. No global installation is performed.

## Run

Native generation was verified with installed Codex CLI `0.162.0-alpha.17.2`. Builds without the required isolation flags fail rather than retry with broader capabilities.

Build Anti-Slope with `npm run build` in its own checkout. Use Node.js 22, Git, and an installed/authenticated Codex CLI. Keep the reviewed repository separate from runtime setup. Save the requirement contract outside the reviewed repository, then run:

```sh
node /path/to/anti-slope/antislope/scripts/session.mjs run \
  --repo /path/to/target --base main --file src/change.ts \
  --requirements-file /outside/target/requirements.txt
```

Repeat `--file` for supporting files. `--codex /path/to/codex` selects an installed executable outside PATH. A relocated skill directory requires `ANTISLOPE_RUNTIME_ROOT=/path/to/trusted/anti-slope`; the helper never imports runtime code from the reviewed repository implicitly. Missing prerequisites fail without installation or answer generation in the main conversation.

The helper emits JSON `preparing`, followed by `ready` and a loopback reader URL. Keep it running in a managed terminal and open that URL. Delete the requirement input file after preparation finishes or fails. Only the author saves the first pass from existing comments and discussion, requests hints, reveals, assesses findings, submits the follow-up, and exports through the UI. Ctrl-C stops the server and preserves a private local checkpoint. Resume with `npm start -- minesweeper resume --session <id>`, using the capability segment of the printed URL as the session ID. The original URL and port are retained.

The facilitating conversation can read permitted state without author actions:

```sh
node /path/to/anti-slope/antislope/scripts/session.mjs status --url http://127.0.0.1:PORT/CAPABILITY/
```

Before reveal this returns only phase, freshness, and random reader ID. After reveal it returns captured clean code, annotations, dispositions, and released initial references. A follow-up reference appears only after the author confirms its discussion snapshot through the inline review card; completed sessions include the handoff. It does not return the mutation replacement field. Never use the browser `/state` or action routes from the facilitating conversation to bypass disclosure.

## Collaborative analysis

Before reveal, the author may discuss code and hypotheses with their AI assistant. Load the filtered view with:

```sh
node /path/to/anti-slope/antislope/scripts/session.mjs discuss --url http://127.0.0.1:PORT/CAPABILITY/
```

The read-only `discussion` endpoint returns requirements, public scenario, saved annotations, displayed baseline/candidate lines, and diff hunks. Candidate text matches the UI's virtual review version in both full-file and diff views. No clean candidate counterpart, hashes, mutation metadata, hints, or reference answers are returned. Status remains a lightweight progress check; discussion reads cannot submit or reveal. Historical sessions retain the same captured review code. After reveal, discussion uses clean code and includes the visible follow-up prompt; released references are available separately through status.

AI can suggest hypotheses, trace branches, propose counterexamples or test cases, and question requirements. Its conclusions are inferred from displayed code and may be wrong; they do not establish which issues were deliberately injected. The author records findings and discusses hypotheses in comments or chat, then saves the first pass without duplicate text fields. Reveal remains explicit. The UI places code and comments on the left and AI discussion plus runtime review actions on the right. Review steps and cards do not open modal dialogs or require duplicate assessment text. Runtime hint replies and released references are displayed as Review messages, separately from AI history and provider requests. A neutral opening summary is generated once, then the author can send questions directly. Saved reader comments are explicitly included when sending, including comments not yet submitted as a first pass. Successful live transcript history and request deduplication IDs are checkpointed in owner-only local runtime storage and restored on server resume. Pending or failed provider turns are not committed. Explicit first-pass submission also freezes the visible discussion and comment ranges in a private browser snapshot. This browser snapshot survives closing the page and is excluded from metadata exports. Server recovery restores live chat and stage separately at the same origin; browser-local comments, ranges and workflow messages remain associated with that URL. Provider requests receive this displayed context and conversation only, never the exercise object or references. Responses are hypotheses, not executed tests. New review-card items are unresolved questions by default. After saving a comment, including before reveal, a separate ephemeral evidence organizer reads only public requirements, captured displayed review code, comments and author messages, without a runtime-provided clean counterpart, baseline, mutation metadata, hints, reference answers or assistant claims. Explicit author messages may include code the author chose to share. Author-reported evidence retains exact source quotations. An actionable comment can also produce a concrete AI counterexample: generated input, predicted behavior, required behavior, branch steps and exact displayed-code citations. This is explicitly labeled unexecuted code reasoning and cannot automatically become a verified clean-code issue. The card displays the reasoning immediately while the session remains reading or submitted. Before reveal it contains no mine counts, location markers or reference answers; generation does not change stage or consume a hint. After explicit reveal the same historical reasoning can explain the exercise region without per-mine confirmation buttons or duplicate author verification text. Missing, disputed or ungrounded reasoning remains unresolved. Records stay in session-scoped browser storage, outside AI chat history and metadata exports; changed sources and upgraded cache schemas require rebuilding them. Confirming the card approves the record, not the truth of its claims. A real issue requires explicit author confirmation using evidence recorded in post-reveal chat; AI assertions are not evidence. Source changes require reconfirmation before export. Follow-up context is retained without inferring an unanswered prediction. Failed turns do not enter history; retries use request IDs to avoid duplicate successful turns. The current limit is an opening summary plus twenty conversational turns.

Before reveal, analysis must use this displayed view rather than reading the clean workspace, Git diff, or snapshot to identify replacements. No virtual code execution or fix generation is supported; verification is reasoning and proposed test cases. Ordinary tests/fixes after reveal use clean code. A conversation that already knows clean source cannot forget it; use the fresh in-page AI discussion, or another fresh conversation with only the discussion view, when blind analysis is required. The bridge still hides private generator material, but it cannot remove prior knowledge or prevent independently inferred defects.

## Isolation and limitations

The bridge starts a fresh [non-interactive Codex invocation](https://learn.chatgpt.com/docs/non-interactive-mode) with ephemeral session handling, a read-only sandbox, disabled execution/integration features, no web search, ignored user configuration, and a private working directory outside the target. It supplies only immutable selected source, the requirement contract, and independent generator instructions, with no parent conversation. Existing CLI authentication is retained, but `--ignore-user-config`, `--ignore-rules`, and `--no-daemon` prevent user-configured MCP servers, hooks, user/project execution rules, and shared daemon state. On supported unmanaged macOS/Linux setups, the built-in default model/provider is used; custom provider/model configuration and system/enterprise/MDM-managed hosts are not supported by this prototype. Known system and MDM configuration paths are checked before starting the worker and fail closed. This check is not exhaustive enterprise-policy detection; do not use this workflow on a managed host. Selected source is transmitted through that default provider. This is an intentional part of requesting the workflow.

Both stdout and stderr are intercepted, including progress, reasoning events, final messages, and errors. Private output uses a strict content schema; the runtime supplies authoritative requirements, hashes, paths, and version binding rather than trusting generated metadata. Structurally invalid output fails with a generic message. Worker output is bounded to 8 MiB, final JSON to 1 MiB, and generation to three minutes. Private temporary files are removed before the reader starts or on ordinary failure/cancellation. Abrupt host termination can leave private temporary files; do not inspect them from the main conversation.

The bridge and stage-gated API prevent routine answer transport into the primary conversation. They are not an OS sandbox against the same user deliberately reading private files/memory or directly using author endpoints. Skills enforce that protocol. No exercise is prepared by an ordinary subagent that sends a free-text completion to its parent. Main-context fallback generation and private-log dumping are forbidden.

Generation checks structural eligibility, not TypeScript semantics, formatting correctness, or truth of references. The worker reasons about supplied source without executing target code or tests. References remain disputable. There is no executable fork, push-capable execution environment, scoring, automatic sharing, behavioral telemetry, or session persistence. Human-curated preparation and preview remain available for more rigorous verification.

## Local recovery boundary

Private checkpoints under `~/.local/state/antislope/sessions/` contain captured clean source and curator references as well as author data. The facilitating conversation must never read or dump them. Resume uses runtime code to validate and restore the private checkpoint without printing its contents. The reader, status and discussion endpoints retain their existing stage gates and filters. Checkpoints are not served as static files or sent to the collaborative provider. Recovery fails generically for corrupt state, unsafe storage permissions or an occupied original port. It does not recapture the workspace or regenerate the exercise; edits become historical through the usual freshness check. Old pre-recovery servers have no checkpoint.

## Streaming chat

Chat replies use a fresh ephemeral Codex app-server over private stdio, using a temporary home that reuses existing file-backed authentication while excluding user config, hooks and shared daemons. Selected tools/features remain disabled and the sandbox is read-only. Only `agentMessage` reply deltas for the active thread are forwarded; reasoning and unrelated events are discarded. Generator output continues through the separate private exec bridge and is never streamed. Completed successful turns alone are checkpointed. Failed or aborted partial replies do not enter later context; the browser preserves the unsent draft for retry. The browser follows the bottom while reading new output and preserves the scroll position when the author moves up through history. The streaming protocol is documented in the [official Codex app-server guide](https://developers.openai.com/codex/app-server).
